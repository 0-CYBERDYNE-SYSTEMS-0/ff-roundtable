Architecture & UX Audit · Independent Review

Does the Roundtable actually behave like an autonomous council?

An audit of the jury / roundtable architecture in Farm Friend Roundtable PRO against the product vision: experts that keep building on each other autonomously, tag each other meaningfully, know when to stop on their own, and let the farmer steer at any moment — or just sit back and read.

2026-09-15 commit daf03ef branch fix/dogfood-gap-remediation 47/47 orchestrator + token-cost tests green
Verdict: the "sit back and read" experience is real; the "autonomous council" is about half-built. The turn-taking engine is solid, tested, and streams beautifully. But three pillars of the vision are not in the product yet: @-tagging is decorative (prompted, but never parsed, routed, or rendered), stopping is mechanical, never semantic (a turn cap plus a repetition heuristic — no agent can conclude the discussion), and steering is deferred and can deadlock (input sent while experts are talking queues until they finish; one click can wedge a conversation in "paused" with no way out short of a server restart).

§2The architecture as built

The orchestrator is an in-memory per-conversation state machine. It is clean, well-commented, and well-tested — the gaps are in what the machine can express, not in its engineering quality.

1 · User message

POST /messages → stored, broadcast. If idle, sequence starts. If busy, the server can interrupt — but the UI queues instead (§1 row 7).

2 · Sequential round

Every expert answers the user message once, in fixed order. Never cut short. Streaming per expert, turn by turn.

3 · Autonomous extension

Up to 2×N extra turns. Next speaker = Moderator LLM suggestion (if a Moderator expert exists) else round-robin. Reference = last expert message.

4 · Stop → idle

Ends by turn cap, or early when a turn is ≥80% trigram-similar to a prior message. Insights auto-generated. No semantic conclusion.

Per-turn contextFull system prompt (incl. ~2.5k-token visualization instructions + farm/weather context) + file context + last 15 messages + reference message.
Speaker choiceSequential: fixed order. Autonomous: 1 extra Moderator LLM call per turn; falls back to round-robin on any failure. @mentions play no part.
Stop signalsTurn cap (2×N) · redundancy ≥ 0.80 Jaccard · user pause/interrupt · error. There is no "we're done" verdict from any agent.
StateIn-memory Map only. Server restart silently kills running rounds; a 5-min staleness guard recovers on the next message. Paused state never expires.

§3Findings

Twelve findings, ordered by severity. "Cosmetic/broken/missing" above are grounded in these.

CRITICAL

F1 · WebSocket broadcasts every conversation to every socket — no authentication, no scoping

The /ws endpoint accepts any connection without checking the session, and broadcastToConversation iterates all connected clients for every event — streaming tokens, full messages, errors — for all conversations of all users. The client filters by conversationId after receipt; the server never restricts who receives what.

For the LAN/Tailscale self-host this is tolerable. For the intended product — which has accounts, paid tiers, and Stripe billing — any party who can open a WebSocket to the server receives every farmer's private conversations in real time. This is the most serious issue in the codebase.

routes.ts:205-236 (no auth on connection)routes.ts:238-336 (broadcast to wss.clients, unfiltered)home-page.tsx:532 (client-side filter)
Fix: authenticate the WS upgrade (same session cookie), track a server-side map of socket → {userId, subscribed conversationId}, and broadcast only to subscribers. Send state_replay on subscribe so reconnects resume mid-stream UI.
CRITICAL

F2 · "Steer at any point" is actually "steer when they finish" — the server's interrupt path is unreachable from the UI

While the roundtable is talking (isProcessing), the client refuses to send: typed messages go into a client-side queue that drains only when the mode returns to idle — i.e., after the full sequential round plus the autonomous extension complete. With 4 experts that's up to 12 serialized LLM turns of dead time for a one-line clarification.

The remarkable part: the server already implements proper steering. A message arriving mid-sequence sets wasInterrupted; the loop finishes the current expert and immediately restarts with the new message. This path is tested (orchestrator.test.ts "Interruption") — it is simply never exercised by the shipped UI. The queue is also client-state only: close the tab and steering messages are gone.

home-page.tsx:261-269 (queue while processing)home-page.tsx:272-284 (drain only when idle)orchestrator.ts:597-608 (server interrupt, unused by UI)
Fix: send immediately on submit and let the server's interrupt machinery do its job; show a "steering — experts will take this next" state. Keep the queue only as an offline/reconnect fallback, persisted server-side.
HIGH

F3 · The paused deadlock: one click on "Disable Auto" can wedge a conversation forever

Full walkthrough in §4. Executive summary: disabling autonomous mode while the council is in its autonomous phase calls pause(); the resume button was removed from the UI; a new user message in the paused state is stored but never restarts the loop; and paused states are exempt from the staleness recovery. The conversation appears alive but no expert will ever respond again until the server restarts.

orchestrator.ts:550-565home-page.tsx:691 ("REMOVED handlePause and handleResume")orchestrator.ts:585-587
Fix: treat a user message in paused mode as an implicit resume (it's an unambiguous steering intent), restore the Pause/Resume controls, and make "Disable Auto" land in idle (finish current turn, stop cleanly) rather than paused.
HIGH

F4 · @-tagging is inert — prompted in, never parsed, routed, or rendered

Experts are instructed to tag ('@[Role Name]', ai.ts:78-80) and the roster is in every prompt, so models do sometimes write tags. But no code path reads them: next-speaker selection is round-robin or a Moderator LLM suggestion that merely reads the raw text of recent messages (a tag may implicitly nudge it — nothing more), and the chat renders tags as plain markdown text. The user also cannot @tag an expert to direct a question.

Consequence: the single most distinctive "council" behavior in the vision — experts summoning each other — is theater. Models are asked to perform an action that has no effect, which also means they have no learned incentive to keep doing it reliably.

ai.ts:78-80orchestrator.ts:215-240 (routing ignores mentions)ChatInterface.tsx:411-413 (plain ReactMarkdown)
Fix: parse @[Role] server-side after each turn → routing priority for the next speaker (mention beats round-robin, Moderator arbitrates conflicts) → broadcast a "mention" event → render as a clickable chip → let the user tag experts in the composer to address a subset (ties into selective wake, F6).
HIGH

F5 · No semantic stop — the council cannot conclude, it can only run out of road

Two stop conditions exist: the hard cap (2×N autonomous turns) and the redundancy trip-wire (≥0.80 word-trigram Jaccard vs any prior message of the sequence — good, cheap, tested). Both are mechanical. The one agent that could judge "this is resolved" — the Moderator — is explicitly constrained to answer with a role name or "RoundRobin"; "conclude" is not in its vocabulary, and the suggestion validator would reject it anyway.

Result: conversations that reached consensus at turn 2 keep going until turn 2N or until someone repeats themselves; and rich discussions that haven't exhausted the topic get clipped by the cap with no synthesis. The "understands when to stop naturally" claim has no implementation.

ai.ts:228-229 (Moderator prompt forbids concluding)ai.ts:807 (validator accepts only roles/RoundRobin)text-similarity.ts:59-88
Fix: extend the Moderator's verdict space with Conclude (plus optional confidence), broadcast a "council concluding" moment, and have the final turn be a Moderator synthesis (or reuse the existing insights generator as the closing statement). Keep cap + redundancy as guardrails underneath.
MEDIUM

F6 · No selective wake — every message is a full fan-out to all experts

"Wake certain experts" has no mechanism: no per-message addressee, no @user-tag routing, no subset selection. Every user message costs N sequential turns + up to 2N autonomous turns + a Moderator call per autonomous turn. A quick "hey Pest Management, thoughts?" summons the entire council in fixed order — slow, expensive, and dilutes the answer.

routes.ts:755-811 (no addressing param)orchestrator.ts:238-240 (fixed full order)
Fix: accepts an optional addressee list; when present, the sequential round includes only those experts (autonomous extension still optional). Natural companion to mention routing (F4).
MEDIUM

F7 · No council-level charter — instructions exist only per expert

Per-expert custom instructions are a solid primitive (schema → modal → prompt). But the vision's "the system can have those instructions" implies governing rules for the roundtable itself — discussion goal, depth, tone, stop criteria, agenda. There is no conversation-scoped field; each expert must be individually instructed, and nothing governs the shape of the discussion.

schema.ts:32ai.ts:63-66
Fix: add a conversation-level charter injected into every expert prompt (and into the Moderator's stop judgment), editable from the conversation header.
MEDIUM

F8 · Orchestrator state is memory-only — restarts kill rounds silently; paused never recovers

Conversation state lives in a module-level Map. A server restart mid-round ends the sequence with no broadcast and no resumption; the staleness guard only recovers states stuck in processing modes (and only when the next message arrives). The paused state is exempt from staleness checks, which is half of the F3 deadlock. It also rules out any multi-instance deployment.

orchestrator.ts:46orchestrator.ts:585-595
Fix: either persist minimal mode state (mode, indices, counters) to the DB per turn, or make state fully derivable from the message log on conversation load.
MEDIUM

F9 · Moderator routing: +1 LLM call per turn, silent degradation, hardcoded legacy fallback models

Every autonomous turn pays an extra Moderator LLM call just to pick the speaker; on any error it silently falls back to round-robin (good fail-open, invisible to the user). The fallback model is a hardcoded legacy slug (mistralai/mistral-7b-instruct), and the insights generator hardcodes mistralai/mixtral-8x7b-instruct — both likely dead on OpenRouter today, meaning insights probably fail silently on fresh installs. Also note the Moderator expert must be manually included in the council (only one preset has it); without one, routing is pure round-robin and nothing tells the user what they're missing.

orchestrator.ts:216-221ai.ts:804ai.ts:754ai.ts:814-817
Fix: config-driven default model for aux calls, surface degradation ("moderator unavailable — speaking in round-robin") via the state channel, and auto-offer a Moderator when composing a council.
LOW

F10 · No "who's next" preview; expert cards have no typing indicator

The chat shows a streaming bubble once tokens arrive, but between turns nothing indicates who is being invited to speak — the council's turn-taking, its most interesting property, is invisible until it happens. ExpertCard has no typing state (the project's own SPEC Phase 2 promised one).

ExpertCard.tsx (no typing prop)SPEC.md:86
Fix: broadcast the chosen next speaker before the turn starts ("Moderator invites Crop Specialist…") and add a shimmer to that expert's card.
LOW

F11 · Every WebSocket payload is console.logged in the browser

console.log("WebSocket received:", parsedData) runs on every event — conversation content accumulates in the browser console (privacy noise, perf noise on long rounds).

home-page.tsx:529
Fix: gate behind an import.meta.env.DEV check or a debug flag.
LOW

F12 · Long-council memory truncation invites repetition

Experts see the last 15 messages (12k chars each); the Moderator only the last 6. In long autonomous rounds early commitments fade from the window, encouraging re-litigation — partially mitigated by the redundancy stop, at the cost of a jarring cut.

ai.ts:512-515ai.ts:796-799
Fix: maintain a running "decisions so far" summary (could piggyback on the insights generator) and inject it instead of raw tail history.

§4Anatomy of the paused deadlock

The one flow in the product that hard-breaks the steering promise. Reproducible from the shipped UI in four steps.

Reproduction: council talking → "Disable Auto" → wedged forever

All steps verified in code at daf03ef; the pause/resume state machine itself is unit-tested, but this composition is not covered.

  1. User sends a message. Council runs its sequential round, then enters autonomous mode (ON by default).
  2. User clicks Disable Auto. disableAutonomous() sees mode = autonomous and calls pause() → mode becomes paused, the running loop stops scheduling turns (orchestrator.ts:550-565).
  3. The UI shows "Status: paused" — but the Resume button no longer exists. It was removed along with pause/resume handlers (home-page.tsx:691). The server's POST /resume endpoint is alive (routes.ts:1100) with nothing that calls it.
  4. User types a message hoping to get things moving. It is stored and displayed — but processMessageTurnBased only starts a sequence when mode is idle. In paused it just updates state and returns (orchestrator.ts:620-627). No expert responds.
  5. Recovery paths that could help, don't: the 5-minute staleness guard explicitly covers only processing_sequential/autonomous (orchestrator.ts:585-587) — paused is exempt; state is memory-only so it survives as long as the process does.
Outcome: the conversation looks alive, accepts and displays messages, and will never produce another expert response — until the server process restarts. One click, no warning, no recovery affordance.

§5What is genuinely working well

Credit where due — the foundation this audit builds on is sound, and recent remediation work (weather resilience, token cost, .ics) was real and verified.

A clean, tested state machine

Mode transitions, sequential order, pause/resume, interruption, stale-state recovery, and the redundancy early-stop are all unit-tested. 47/47 orchestrator + token-cost tests pass at the audited commit; the repo claims 331 green overall.

The lurking experience is real

Token-by-token streaming with per-expert bubbles, avatars, live mode badges, queue count, and reconnect handling that refetches persisted messages. Watching the council work is genuinely pleasant.

Steering machinery exists server-side

Interrupt-and-restart with newest-message-wins is implemented and tested. The gap is that the UI never invokes it (F2) — the hard part is already built.

Honest failure surfaces

Errors persist as real messages (survive refetch), vision-rejecting models get an honest per-expert explanation, duplicate sends don't re-trigger fan-out, and weather degrades with typed, cached reasons.

Token-cost remediation shipped

The dogfood gap pass delivered: redundancy early-stop (0.80 trigram Jaccard), duplicate-submission gate, and analyze-image-once (base64 embedded once per conversation, text note thereafter).

Contextual grounding

Farm profile (crops, soil, acreage, location) and live weather are injected into every expert prompt, with per-expert custom instructions as a bonus steering surface.

§6Remediation roadmap

Sequenced so each phase compounds: unbreak what exists, then make the council real, then polish the theater of it.

P0 Unbreak steering & privacy

The vision's two non-negotiables — the user can always steer, and conversations are private.

F2
Wire the UI to the server interrupt path

Submit immediately on send; the running sequence finishes its current turn and restarts on the steering message. Show a "steering at next turn" state. Keep the client queue only as a reconnect fallback.

F3
Kill the paused deadlock

User message in paused mode ⇒ implicit resume. "Disable Auto" lands in idle (finish current turn, stop cleanly). Restore Pause/Resume controls. Add a regression test for message-in-paused.

F1
Scope the WebSocket

Authenticate the upgrade, subscribe sockets server-side to {user, conversation}, broadcast only to subscribers, replay state on subscribe.

P1 Make the council real

Turn the vision's three signature behaviors from prose into mechanics.

F4
Mention mechanics, end to end

Server-side @[Role] parsing → next-speaker priority → "mention" WS event → clickable chips in chat → composer autocomplete. Experts' tags then do something, which also makes them reliable.

F5
Semantic conclusion

Moderator verdict space gains Conclude; on it, broadcast a "council concluding" moment and finish with a synthesis turn. Cap + redundancy stay as guardrails.

F6+F7
Selective wake + council charter

User @tags (or an addressee picker) restrict the sequential round to the addressed experts. Conversation-level charter (goal, depth, stop criteria) injected into every prompt and the Moderator's judgment.

P2 Polish & hardening

Make the roundtable legible and operationally boring.

F8
Survivable orchestrator state

Persist/derive mode per turn so restarts resume cleanly and multi-instance is possible.

F9
Aux-call hygiene

Config-driven models for Moderator/insights (drop hardcoded legacy slugs), surface routing degradation in the UI, offer a Moderator when composing councils.

F10–F12
Legibility

Next-speaker preview chip + card shimmer, quiet console logging, running decisions-summary instead of raw tail history.
